# DBLP runtime and resource qualification

The adopted seven-arm DBLP v2 driver requires **Torch 2.1.2**, and the qualified one-GPU repository supplies **Torch 2.1.2+cu118 / Python 3.11.14**. Its actual model path is a Torch implementation: `dblp_inputs.materialize` creates `HeteroGraph` with Torch edge/features, `families.build` creates `NativeHGT` / `PrivateHGT`, and `hgt_private.relation_sum` uses Torch scatter operations. None of that import closure imports DGL. No CUDA DGL installation is needed to run these seven arms. The source, exact imported modules and freeze hashes are recorded in `BINDINGS.json`.

DGL 1.1.3 from `.gnnm_runtime/hgb_dgl_cpu_v1/site` remains the separately qualified CPU actual-author correspondence environment. Its CPU wheel does not establish CUDA graph support. The native environment DGL import previously failed for missing `libcusparse.so.11`; that failure does not affect this Torch-only seven-arm path. The saved 18.77 qualified runtime uses Torch 2.7.1 and has no saved DGL CUDA qualification, so it does not satisfy the exact driver version without a separate runtime amendment. No 18.77 or seven-GPU connection, package download or installation was made for this task.

`qualify_resource.py` uses the exact adopted freeze and all seven seed131 geometries. It streams only the bound full DBLP node/link members, reads the existing explicit TRAIN_VAL_ONLY source pool, and constructs only the first frozen split's 974 TRAIN loss targets. It never constructs validation targets, scores validation/test labels, selects a checkpoint, opens ZIP label/test members, or calls training driver main. One disposable AdamW/OneCycle update and one unscored evaluation forward per arm measure materialization, training and checkpoint costs. The resulting saved states are qualification artifacts and cannot be adopted as study fits.

The checkpoint custody check uses the pinned data-only OneCycle state and `weights_only=True`, exact model/optimizer parameter names, all member dropout states and caller CPU/device RNG. The previous synthetic CPU fixture's seventeen-step future trajectory remains separately bound; it is not repeated here. All seven models are initially resident as in the actual driver. RSS/peak receipts describe process lifetime and order, and are not isolated-arm efficiency measurements.

CPU invocation is authorized through `run_cpu_remote.py` on the anogena-2 account and exact one-GPU inventory. CUDA is hidden, all thread settings are one, address space and observed RSS are bounded by 8GiB, and wall/CPU time by 600 seconds. It first screens available host/cgroup RAM and load. Every failure and partial arm terminal is retained. The forecast uses measured per-family full-graph epoch + unscored eval + worst-case checkpoint-write cost, repeated over five seeds and 300 epochs each (10,500 case-epochs), with a separate factor2 planning allowance.

GPU qualification remains closed until root reports original cohort completion and supplies an explicit GPU qualification release binding freeze, packet manifest, run name and fixed UUID. CPU measurements are not GPU measurements. Source inputs, training packet, root freeze and Photo packet are preserved.
