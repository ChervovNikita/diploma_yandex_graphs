# Preparation checks and checks during execution

**The new scientific run still requires the user's explicit GO.** Preparation must produce a finite executable source/data/role/configuration roster, required references, paid stage dependencies, resource reservations, reproducible environments, fixed GPU assignments and start commands. All original-five dataset experiments remain excluded.

Preparation checks cover source correctness, selected-configuration propagation, checkpoint/state reconstruction contracts, input custody, dependency ownership, failure preservation, runtime compatibility and representative maximum-shape memory. They can use synthetic CPU fixtures and bounded random-state engineering calls. Such calls do not certify accuracy, convergence or the behavior of learned states.

Actual trained-parent checkpoints, measured whole-fit convergence and costs become available only during the approved scientific run. Requiring these outcomes before GO would require running the study before approval. They are runtime checks and reportable outcomes, not results that preparation may fabricate.

Every acquisition in the approved roster must genuinely complete its paid training before a continuation can load its selected checkpoint. Verify its positive selected step, complete source budget, configuration, actual bytes and hash at runtime. Restore or custody failures stop dependent work; untrained resource prototypes never replace this authority. Whole-search and complete-family barriers continue to govern selection, comparison and scored release.

Maximum-shape engineering measurements and explicit safety margins support prospective memory reservations. Actual kernels, values and concurrent load can still cause failure. The runtime must retain that failure and its cost, and must not quietly shrink the architecture, cut training, change the objective or retry a failed fit. Slot admission respects available memory and other work. Two configured slots do not guarantee two simultaneous large fits or twice the throughput.

The user requested preparation on the allocation before later synchronization to 18.77. The transfer manifest and execution code can be prepared now. Live 18.77 identity, environment, disk and GPU admission checks belong to the later authorized synchronization. Those operational checks must not change approved datasets, methods, search domains, seed roles or training criteria. A scientific scope change needs a newly enumerated plan and approval.

Preparation is not complete while required developed methods lack executable workers or their exact finite scopes remain unresolved. Untrained proposals and diagnostic history must be distinguished from fitted scientific methods, preserved in the inventory, and explicitly scoped instead of being silently counted as successful approaches or deleted.
