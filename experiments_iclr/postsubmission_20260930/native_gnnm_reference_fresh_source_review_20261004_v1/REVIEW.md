## Findings

**F1 — [P2] Verify the input identities inside the paired protocol before admitting the reference.** In `native_driver.py:45–60`, `validate_context` checks that the caller’s context matches this live bundle, features and validation-label digest. It then reads the bound paired protocol but checks only `native_gnnm_manifest_sha256` and `bank_manifest_sha256`. It neither requires a paired-input schema nor compares any paired role, feature, native-graph or validation identity to the live context. Consequently a two-hash document qualifies as the paired protocol, and a document declaring different input identities also qualifies. The manifest hashes bind the source packages, including their protocol files; the missing check concerns the shared input identity rather than an additional redundant source hash.

This falls short of `PROTOCOL.json:25`, which calls for both manifests **with paired role/feature/native graph/validation identity**, and leaves a future paired accuracy comparison able to use different inputs while passing this function. The protocol is explicitly pending, so this is not evidence of an actual mismatched study. It is a source admission defect to fix before that study is qualified. Require a defined paired protocol schema, a matching fixed block, and its role/features/native-graph/validation identities; compare those values with the already checked live context. A separately bound bank input/freeze record can supply the bank side of the pairing.

Evidence: the stdlib-only `check_paired_protocol_gate` in `source_review_checks.py` patches only the numerical feature hasher to an explicit synthetic identity and uses a small synthetic stdlib bundle. The current function accepts both a paired document with conflicting identity fields and a document omitting those fields entirely. `SOURCE_CHECK_RESULTS.json` records both admissions as `true`. This check tests the admission branch; it performs no neural computation or scientific fitting.

**F2 — [P2] Reject unsupported device types or capture their device RNG before claiming live-RNG/full-state restoration.** `bank.resolve_device` at `bank.py:22–26` accepts any `torch.device` type. The new driver uses it at `native_driver.py:79`. `bank.rng_state` at `bank.py:42–49` captures Python, NumPy, CPU Torch and the selected CUDA stream only; `restore_rng` at `bank.py:52–66` has the same inventory. An MPS device is therefore admitted while its stochastic device stream is absent from snapshots and restoration. On an admitted MPS implementation, dropout’s MPS stream would not be restored for exact next-update replay or explicitly preserved across the transition.

`README.md:9` and `PROTOCOL.json:44` state live-RNG preservation without this device limitation. The unrun tests are explicitly synthetic CPU checks (`README.md:13`); they do not establish other device support. Preserve the byte-identical bank reuse by restricting device types in the new native entry to CPU and selected-device CUDA until another device’s state support is implemented and qualified, and document this limitation. CUDA numerical determinism/resource behavior remains pending independently.

Evidence: `check_device_rng_gate` uses stdlib stubs, admits `mps`, and confirms that neither MPS RNG capture nor MPS RNG restoration is called. The result is recorded in `SOURCE_CHECK_RESULTS.json`. No numerical backend was imported or executed.
