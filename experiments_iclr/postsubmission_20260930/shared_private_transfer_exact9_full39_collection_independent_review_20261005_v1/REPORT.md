## Concrete defects

### F1 — Medium (P2): the purported complete source pass does not close external executable dependencies

`collect_companion.py:110-117` verifies the entries in a manifest's `files` list. `source_packet:156-159` invokes that helper for the training packet and binds its `run.py`. The all9 pass calls it at line 312. It does not authenticate the external dependency set used by the bound training custody source, nor does it traverse the external native donor source manifest.

The bound actual singleton `custody.py:22-29,87-92` pins an external native donor manifest, geometry manifest and implementations, and the recursive-adjoint source. It explicitly hashes every file in the native donor manifest before a fit. `custody.py:124-137` then imports or loads the external native model, donor heads, geometry, cycle, and adjoint code. Those external paths are outside the companion training directory. The new collector's manifest-relative file checks do not reconstruct that closure. The operational `singleton/pilot_common.py:104-108` also pins and imports a separately located supervisor whose Popen ownership implementation is not authenticated by this collector. The GPU77 operational helper has the analogous source-pinned supervisor mechanism.

The original30 path has a related concrete omission: `inventory_full39_histories.py:114-118` hashes every declared `numerical_science_files` reference, including the native donor `SOURCE_MANIFEST.json`, but does not hash that manifest's member files. Binding a manifest's bytes alone does not authenticate the referenced external native model/head bytes. Consequently a changed or missing external member file need not prevent `authenticate_all39` from returning, and the next step may hash histories while the claimed full source closure remains incomplete. The static source could still have checked those bytes when the historical fit ran; this finding concerns the advertised retrospective reauthentication, and does not establish historical numerical corruption.

Before an enabled successor asserts complete source custody, authenticate the precise external dependency manifests and executable member files, plus the actual queue supervisor source, through ordinary byte/hash checks. Preserve genuine phase-relative source-copy provenance. Keep these checks in the all39 authentication closure before history observation and in any required D2 source custody gate. No imported code, executable AST extraction, fabricated source manifest, or qualification rerun is needed to perform those byte checks.

### F2 — Medium (P2): original30 terminal reauthentication lacks the link to its actual reviewed queue process/source

`inventory_full39_histories.py:153-201` binds the original donor queue/release/plan/block and validates every child job, completion, child argv/cwd/session identity, and byte-identical saved `EXIT.json`. These are useful checks. It does not authenticate the operational source identified by `q['pilot_source_manifest_sha256']` or bind that actual provider queue source to a reviewed operational packet. The original30 path also does not read its genuine `QUEUE_START.json` or `.CHILD_STARTED.json`, compare supervisor identity to the child ppid/start ticks, or verify same-host queue-start → child-start → owned-exit chronology. The bound original `run_queue.py:148-150` emits queue-start identity and `run_fit` emits child-start identity. The source ownership string in the retained EXIT and its equality to the registry/block receipt cannot itself perform this missing link. The exact9 implementation does perform the corresponding checks (`collect_companion.py:316-329,380-395`).

Thus an original30 receipt containing an otherwise acceptable child identity with an unrelated ppid/start time, or a donor queue identifying an unbound operational source, is not rejected by this reauthentication path on those grounds. This is a completeness defect in the stated all39 owned-terminal/source gate; it is not evidence that any existing receipt actually has such a defect. The original registry's prior independent custody authority is retained, but the new pass does not itself supply the missing recheck.

Authenticate the actual original provider queue/supervisor source and the genuine source-emitted queue-start and child-start records. Check their process identities, argv/cwd, child-parent/start-tick link, and same-host chronology before accepting original30 custody. Use available historical records or keep the requirement unresolved; do not manufacture a historical launch/admission filename or retroactively label a derived record as pre-fit authority.
