# PubMed LM4 whole-acquisition watcher — source only

This disabled watcher adapts the GRU route, receipt, source and process-birth checks and its direct readout-owner TERM/KILL/wait/reap lifecycle. It targets the sealed LM4 execution and separate reader v2. It imports no model, launches no fit or qualification, offers no retry, and uses no scientific gate to choose whether readout proceeds. Preparation of this package reads no arrays, current truth or remote state. Producer and reader seals remain unchanged.

Root activates only after the actual acquisition starts. In a separate CONFIG and root decision, bind the acquisition CONFIG/start/ACTUAL_LAUNCH receipts, actual owner/child birth triples, successful v2 preparation CONFIG/start/end/custody, successful qualifier CONFIG/start/end/report, watcher manifest, reader manifest, output and finite envelopes. Acquisition must be in activation_root_20261011_v2/acquire; the exact successful preparation leaf is bound by root. Placeholder receipts and zero birth triples are unusable.

The watcher reads no partial panel, predictions, trace or child log while waiting. It first verifies the exact acquisition owner's successful complete exit, worker reaping/CUDA absence and produced PANEL receipt. The sealed reader's metadata-only close_panel then requires all36 fresh banks,54 trajectories and39 endpoints, source/ancestor/cache relations and stage1-before-stage2 closure. Only then it fills the sealed CAL template, directly owns and waits its finite owner, and closes all39 fresh500-update temperatures (19,500 scalar updates; no inherited CAL). It always proceeds to the sealed whole DEV reader after successful CAL closure. Gate values never control handoff or watcher success.

Outputs are WHOLE_FAMILY_CLOSURE.json, ALL_CAL_CLOSURE.json, generated stage CONFIGs and direct owner transports/start/end receipts, WATCH_END.json and score_v1/DEVELOPMENT_REPORT.json. Whole DEV closure requires39 rows and156 comparisons with complete release/producer linkage. The watcher never opens role targets itself.

Finite envelopes match the GRU lifecycle:604,800 seconds acquisition wait,30-second polling,7,200 seconds each CAL/DEV worker,619,380 seconds whole watcher,16GiB RSS/32GiB CUDA reader limits. Twenty seconds are reserved for bounded cleanup of this watcher's own readout owner/worker only. It never kills acquisition. Root launches watcher.py CONFIG.json using the allocation repository's ordinary Python; source templates stay disabled and sealed.
